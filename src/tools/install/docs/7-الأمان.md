# ٧. الأمان

## المفاتيح

| المفتاح | أين يوضع | ملاحظة |
|---|---|---|
| **Publishable / anon key** | داخل `index.html` | عام بطبيعته، آمن أن يظهر. الحماية لا تعتمد عليه |
| **service_role / secret key** | **لا مكان له أبداً** في البرنامج أو المستودع أو أي ملف ترسله | يتجاوز كل الصلاحيات. لو تسرب: Supabase ← API Keys ← أنشئ مفتاحاً جديداً واحذف القديم |
| كلمة مرور قاعدة البيانات | عندك فقط | لا يحتاجها البرنامج |
| كلمة مرور تطبيق Gmail | في إعدادات SMTP في Supabase فقط | تقدر تلغيها من حساب Google في أي وقت |

## كيف تُحمى البيانات

- **كل شركة معزولة:** قواعد RLS في قاعدة البيانات تمنع أي مستخدم من رؤية سجلات شركة ليس عضواً فيها — حتى لو عدّل الكود في متصفحه.
- **الصلاحيات تُفرض في قاعدة البيانات:** كل ترحيل يتم بدالة تتحقق من «اعتماد» القسم قبل كتابة أي قيد.
- **الدخول بالدعوة فقط:** لا يستطيع أحد إنشاء حساب إلا ملاك النظام (`owner.sql`) أو من وصلته دعوة.
- **المرحّل لا يُعدَّل ولا يُحذف**، وكل تغيير مهم يُسجل في سجل التدقيق.
- **الاسترجاع محمي:** يرفض الملفات المعدّلة أو التي تشير لبيانات شركة أخرى.

## توصيات

1. فعّل **التحقق بخطوتين** على حسابات Supabase و GitHub و Google — من يملكها يملك النظام.
2. لا تعطِ صلاحية «المستخدمون» إلا لمن تثق به — يقدر يدعو ويغير الأدوار.
3. **ملفات النسخ الاحتياطي فيها كل بيانات الشركة** (عملاء، رواتب، أرصدة): احفظها في مكان آمن، وشفّر قرص كمبيوتر النسخ (Ubuntu: خيار «Encrypt» عند التثبيت).
4. حساب النسخ الاحتياطي: استخدم دور «النسخ الاحتياطي» فقط — لا تستخدم حساب المالك على كمبيوتر النسخ.
5. عند خروج موظف: **المستخدمون ← إزالة** فوراً.
6. الفوترة الإلكترونية: لا تسترجع نسخة **كشركة جديدة** وتستخدمها لإصدار فواتير بنفس الرقم الضريبي بجانب الأصلية — سلسلة الفواتير يجب أن تكون واحدة.
